UART is one part of the physical interface

A portable TIOL112 control driver is now available. Its host tests cover SIO polarity, transmit release, wake-up consumption, diagnostics and initialization failures. The driver and reference application also compile as Cortex-M0+ GCC objects. This evidence covers reusable C code; a target still needs its MCU callbacks, wiring and physical tests.

The MCU UART transports bytes. A physical IO-Link design also needs the transceiver, supply and C/Q circuitry, control and fault GPIOs, wake-up handling and measured timing. The projects include portable TIOL112 and L6362A control drivers; their electrical behavior still needs analog Twin and physical validation.

LabWired Twins

Every hardware reference is intended to have a runnable LabWired Twin executing its firmware with analog IO-Link effects. That verification is pending for these projects. It must include C/Q voltage and edge behavior, cable loading, supply faults and transceiver response; a UART byte exchange alone does not satisfy it. Model results and physical measurements will be reported separately.

Before a physical bench test

Record your exact MCU board, transceiver board/revision, pin connections, firmware commit and toolchain. Use the vendor wiring and power documentation, then capture a commercial master's model and firmware, IODD, COM mode, process-data sizes and test results. Publish logs for startup, cyclic data, ISDU, events and reconnect behavior. See the physical validation checklist.

The standalone master stack is a separate software project. Running it against the device stack in simulation is useful protocol testing; it is not evidence from a commercial physical master.
